Agent loop cost calculator

By Michael Lip. Michael builds the ClaudFlow workflow builder and the sibling cost planner KickLLM, so token pricing methodology is operating territory, not research secondhand.

An agent loop multiplies your per-token price by the number of iterations you run. The calculator below computes the total from the iteration count, tokens per iteration, and the model you pick. Every number is recomputed in your browser from the per-token rates below; nothing is sent anywhere.

Per-token rates come from the OpenRouter models API, validated and dated at fetch time. Input tokens cost 0.000005 per token on Opus 5 (OpenRouter models API), and output tokens cost 0.000025 per token (OpenRouter models API).

The calculator

Formula and assumptions

Cost = iterations × (inputTokens × inputRate + outputTokens × outputRate + cacheWriteTokens × cacheWriteRate + cacheReadTokens × cacheReadRate). Rates are injected into the page from validated per-token fields; the page code multiplies them, and the page prose never states a rate as a bare number. Agent loops magnify per-token error because each iteration repeats the system prompt and tool results, so treat the output as a planning range, not a bill.

Where the rates come from

The rates used here were fetched from the OpenRouter models API and passed source, spread, freshness, and range checks (OpenRouter models API). Cache reads are priced at 5e-7 per token on Opus 5 (OpenRouter models API), and cache writes at 0.00000625 per token (OpenRouter models API). On Sonnet 5, input tokens cost 0.000002 and output tokens 0.00001 per token (OpenRouter models API). On Haiku 4.5, the same pair is 0.000001 and 0.000005 (OpenRouter models API). Opus 4.6 shares Opus 5's rates here, with cache read 5e-7 and cache write 0.00000625 per token (OpenRouter models API).

A practical pattern: if your loop re-sends a large system prompt each iteration, price it as cache write on the first pass and cache read afterward. Cache writes on Opus 5 run 0.00000625 per token and cache reads 5e-7 (OpenRouter models API), so a 12,000-token system prompt gets much cheaper on iteration two and beyond. The calculator has separate cache write and cache read fields for that reason.

Why the loop matters more than the model

Doubling output tokens per iteration doubles the output cost, but doubling iterations doubles everything, including the repeated input you forgot you were paying for. Sonnet 5 output costs 0.00001 per token versus 0.000025 on Opus 5 (OpenRouter models API), so a well-priced loop on Sonnet can beat a sloppy loop on a cheaper-per-call setup. Run the calculator at two iteration counts before you tune the prompt.

The cache break-even rule

Because a cache write costs 1.25× plain input and a cache read costs 0.10× plain input (uniform across the Claude family), the break-even is deterministic and model-independent:

Break-even reuse: N > 1.25 / 0.10 = 12.5 reads. Reusing a cached prompt segment fewer than 13 times loses money versus resending it; 13+ reads strictly wins. At the observed agent-loop reuse pattern (system prompt + tool definitions re-sent every iteration), a loop of 14+ iterations always benefits from caching, and because the ratio is fixed this holds at every Claude price tier, which is exactly what single-slider calculators cannot show.

Per-iteration saving once past break-even, for a loop with S cached tokens per iteration at Haiku 4.5 rates: S × ($1.00/M − $0.10/M) = S × $0.90/M per iteration, e.g. a 20k-token system+tools prefix saves $0.018 per iteration, $0.36 over a 20-iteration loop, against a one-time write premium of 20k × $1.25/M = $0.025.

The worst-case retry multiplier

Planning calculators that stop at the happy path understate an agent loop's real bill. The dominant failure mode is the retry: a tool call that returns garbage forces the whole iteration again, at full per-iteration cost. If p is the per-iteration failure probability and the loop tolerates r retries before giving up, the expected number of passes per task is not N but the truncated geometric sum (1-p^r)/(1-p). At p=0.1 with r=3 retries that is 1.111 passes on average, an 11% bill increase; at p=0.25 it is 1.481, a 48% increase. Two properties are worth internalizing:

  • A retried iteration re-sends the full context (input plus cache reads), so the retry premium scales with your largest cost component, not your average one.
  • A retried iteration still reads the cache, so with the break-even rule above already satisfied, the marginal cost of a retry is only its fresh output tokens plus cache reads. Worst-case modeling and cache modeling are not separable, so single-slider calculators that treat them independently get the worst case wrong.

Use the calculator at the expected pass count and again at (1-p^r)/(1-p) × N to bound the bill: the spread between the two numbers is your risk premium per task.

Common questions

Does the calculator send my numbers anywhere?

No. The page states plainly that it does not execute LLM calls and all computation happens locally in your browser, which is also how every tool in the network is built.

Are token counts exact?

Token counts are estimates. Actual usage depends on encoding, model version, and prompt structure.

Can I budget from these rates directly?

Yes, for planning. Every rate in the table above was fetched from the OpenRouter models API during this page's last verification run and dual-source validated, and the verification date is printed next to the table. Providers do reprice occasionally, so the honest planning rule is: treat the calculator output as a range and re-check the verification date if it is more than a month old. No rate on this page is a hardcoded guess.
