How the math works

Today, an unstable prefix pays full input price on every request. Refactored, the first request writes the static prefix at the cache-write rate and every later request reads it at the cache-read rate, paying full price only on the dynamic tail.

What moves the number

  • Stable system prompt - written once, never templated. No dates, no counters, no session IDs.
  • Tool schemas in a fixed order - a reordered tool list is a changed prefix.
  • Large reference docs - specs and retrieved context that survive the whole session.
  • Few-shot examples - frozen examples before live conversation.
  • Conversation history - appended to, never rewritten mid-session.
  • Dynamic user data and timestamps LAST - where they cannot invalidate anything above them.

Frequently asked

Does prompt order really matter for caching?

Yes. The prefix cache is byte-exact from token 1. A single changed token at position 100 invalidates everything after it, so a timestamp near the top of the system prompt silently uncaches the whole prompt, including tool schemas and reference docs below it.

What if my dynamic data is large?

Only the stable prefix caches. If dynamic tokens outweigh static ones, most of every request still bills at full input price. Summarize volatile content or externalize state to a tool call so it never enters the prompt.

Does the first request cost more after refactoring?

Slightly. The first request pays the cache-write rate on the static prefix instead of the input rate - a one-time premium amortized to nothing across thousands of requests.

How is this different from just shortening the prompt?

Trimming tokens saves once per request; ordering saves on every request without removing anything. You keep the full reference docs, and the static prefix still bills - at the cache-read rate instead of the input rate.
