How the math works

Parallel cost is serial cost times the session count. Cost scales linearly with N; wall-clock time does not, because merges, review, and integration gates stay serialized. The cap runway is the cap divided by daily fleet burn.

Where the multiplier hides

  • Git worktrees with N agents — one branch per agent looks tidy, but every worktree is a full-rate session re-reading the same large context.
  • Background subagents you forgot — fire-and-forget calls keep billing after the main session looks idle.
  • Retry storms under concurrency — parallel sessions hitting rate limits re-send full context on every retry.
  • Monitoring loops — an agent polling a dashboard on a timer bills while producing zero deliverables.
  • Orphaned tmux panes — the session you detached yesterday is still running its loop.

Frequently asked

How many parallel Claude Code sessions can I afford?

Invert the formula: sessions = cap / (rate x 60 x hours_per_day x days). At $0.021/min and 6 sessions, a $200 cap buys about 26 hours of fleet time - barely over one working week at 5 hours a day.

Do parallel agents actually finish faster?

Wall-clock, yes, for genuinely independent tasks. But serialized gates (merges, review, integration) cap the real speedup, while cost always scales linearly with session count. You pay 6x and finish somewhat less than 6x faster.

Does prompt caching soften the parallel cost?

No. Each session has its own context and its own cache. Caching makes each session cheaper per turn, but the N-way multiplication sits on top. Six cached sessions still cost six times one cached session.

Why is the overage larger than the serial cost?

Because the baseline is small. One session at $0.021/min for 5 hours a day is about $10.50/day, easy to ignore. Six sessions is $63.00/day of the same habit; with N=6, five-sixths of the bill is pure concurrency premium.
